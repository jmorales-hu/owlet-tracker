Redirects `/wayfinder` from GitHub Issues to owlet. Until a work repo's
`docs/agents/issue-tracker.md` points at owlet, `/wayfinder` keeps writing its maps to GitHub
Issues and owlet's Map stays empty for that Thread.

Run this from inside the work repo you want to redirect — not from inside `owlet-tracker`
itself. This repo's own `docs/agents/issue-tracker.md` is the real GitHub-issue-tracker file
for owlet-tracker's own issues (see `docs/agents/domain.md`, `triage-labels.md`) and must stay
as it is.

## Steps

1. **Resolve the `owlet` CLI location**, following Intake's
   [Locating the binary](../intake/SKILL.md#locating-the-binary) procedure as-is. One
   difference: don't leave the result as `$CLAUDE_PLUGIN_ROOT/dist/owlet` for later expansion.
   That variable is only set while a skill from the `owlet` plugin is running, and `/wayfinder`
   is a skill from a different plugin — by the time it reads the file this skill is about to
   write, the variable is gone. Bake the resolved invocation in as a literal string now.

2. **Ensure `docs/agents/` exists**: `mkdir -p docs/agents`. Don't fail if it's already there.

3. **Write `docs/agents/issue-tracker.md`**, overwriting it completely with the template in
   [The template](#the-template) below, substituting the resolved invocation from step 1
   everywhere `<owlet>` appears. This skill owns exactly this one file — never touch
   `docs/agents/triage-labels.md` or `docs/agents/domain.md`; those belong to
   `/setup-matt-pocock-skills`.

4. **Report the path written.** Note that the file doesn't self-update: re-run `/owlet-setup`
   after the `owlet` CLI surface changes (new commands, renamed flags) to regenerate it.

Running this twice writes the same bytes both times, provided `owlet`'s resolution (PATH vs.
`$CLAUDE_PLUGIN_ROOT/dist/owlet`) hasn't changed on this machine — safe to re-run.

## The template

Copy this verbatim into `docs/agents/issue-tracker.md`, replacing every `<owlet>` with the
invocation resolved in step 1.

```markdown
# Issue tracker: owlet

Generated by `/owlet-setup` from the `owlet` plugin — don't hand-edit. Re-run `/owlet-setup`
after the `owlet` CLI surface changes; it overwrites this file completely.

This file only covers `/wayfinder`'s wayfinding operations. owlet has no general-purpose
create/list/label/close surface for arbitrary issues, so skills that expect one (e.g.
`/triage`) have no owlet equivalent here.

Every command below is already written with the `owlet` invocation resolved when
`/owlet-setup` last generated this file. If commands start failing because the binary moved,
re-run `/owlet-setup` rather than editing the paths below by hand.

## Wayfinding operations

Used by `/wayfinder`. A map lives inside an owlet **Thread** — the Thread's **Map** is its
Tickets and the Blockers between them. Run `/wayfinder` against a Thread already opened by the
`intake` skill from a Jira ticket, and use that Thread's key (e.g. `OWL-5`) everywhere a map is
referenced below.

- **Map**: `<owlet> map <KEY>` — the Map's Tickets, layered by depth, with the Frontier
  marked. This is the low-resolution view `/wayfinder` loads once per session.
  Gap: owlet has no command to create a freestanding map. A Thread — and so its Map — comes
  into being only through Intake, from a Jira ticket (`<owlet> thread new <KEY> --route drive
  --title "<title>" --branch <branch>`). A `/wayfinder` effort that starts from a loose idea
  with no Jira ticket behind it has no home in owlet; don't invent a `map new` to make one.
  Gap: owlet's Thread has no Destination, Notes, Decisions-so-far, Not yet specified, or Out
  of scope sections — only the Jira description captured at Intake. There is nowhere in owlet
  to write them.

- **Child ticket**: `<owlet> ticket new <KEY> "<title>" [--blocked-by <ID>,<ID>]`. Prints the
  allocated Ticket ID on stdout — that ID is the Ticket's identity, the same role `/wayfinder`
  gives the tracker's issue id.
  Gap: a Ticket has a title and a status, nothing else — owlet has no field for a Ticket's
  Question body. Fold the question into the title; there's no better place to put it.
  Gap: owlet has no Ticket type — no equivalent of the `wayfinder:<type>` label
  (`research`/`prototype`/`grilling`/`task`, or the HITL/AFK split it encodes). Don't invent a
  flag for it; track the type in the title or in the session, not in the Store.

- **Blocking**: `<owlet> blocker add <KEY> <ID> --blocked-by <BLOCKER-ID>` to add a Blocker,
  `<owlet> blocker rm <KEY> <ID> --blocked-by <BLOCKER-ID>` to remove one. This is owlet's
  native `blocked_by` edge, and it rejects cycles. A Ticket is unblocked when every Blocker on
  it is Done.

- **Frontier query**: `<owlet> frontier <KEY>` — the Open Tickets whose every Blocker is Done,
  in Ticket ID order; first one wins. Add `--json` for machine-readable output.

- **Claim**: `<owlet> ticket claim <KEY> <ID>` — marks the Ticket Claimed. Claimed Tickets are
  excluded from the Frontier, the same role an assignee plays in `/wayfinder`'s
  tracker-agnostic model.
  Gap: owlet is a personal tracker with no assignee concept — Claimed doesn't say *who*
  claimed it, only that someone has. That's fine for a single dev; it stops matching
  `/wayfinder`'s "concurrent sessions skip claimed tickets" story the moment more than one
  person drives the same Thread.

- **Resolve**: `<owlet> ticket done <KEY> <ID>` — marks the Ticket Done.
  Gap: owlet has no comment or answer field on a Ticket, and the Thread has no
  Decisions-so-far section to append to. There is nowhere in owlet to record the resolution
  text or a context pointer — `/wayfinder`'s "post the answer, then append a context pointer
  to Decisions-so-far" step has no owlet write to make. Keep the answer wherever `/wayfinder`
  already keeps assets (the branch, the linked artifact); owlet only records that the Ticket
  is Done.
```
